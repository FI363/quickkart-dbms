Advanced scope

Individual project

# 3. Database architecture and ER design

I recommend designing the database around these eight logical domains:

1. Identity and access management.
2. Customer and address management.
3. Product catalogue.
4. Dark store management.
5. Inventory management.
6. Shopping cart and order management.
7. Payment and refund management.
8. Delivery management.

We will use approximately 24–26 tables. That's substantial enough for an advanced DBMS project, but still manageable.

Important relationship decisions:

- A product can have multiple variants.
- A product variant can be stocked at multiple stores.
- A customer can have multiple addresses.
- A customer can place multiple orders.
- An order contains multiple order items.
- An order can have multiple payment attempts, but only one successful payment should be accepted.
- An order can have one delivery assignment at a time.
- Every stock reservation is associated with an order and product variant.

We'll also implement stock transfers between stores as an additional feature.

## 3.2 Relational schema

Let's define the actual tables.

We'll use:

- `BIGINT UNSIGNED AUTO_INCREMENT` for primary keys.
- `DECIMAL(10,2)` for money.
- `DATETIME` for timestamps.
- `VARCHAR` for statuses with controlled values.
- Foreign keys for referential integrity.
- Unique constraints to prevent duplicate records.

# 4. Normalization strategy

We will target Third Normal Form (3NF) for the database.

| Normal form | How we apply it                                                  |
| ----------- | ---------------------------------------------------------------- |
| 1NF         | Each column contains atomic values; no repeating product columns |
| 2NF         | Every non-key attribute depends on the complete candidate key    |
| 3NF         | No transitive dependencies between non-key attributes            |

A few design decisions worth noting:

- Product details are separated from variants.
- Categories and brands are independent entities.
- Store inventory is separated from the product catalogue.
- Order items are separated from orders.
- Payments and refunds have independent records.
- Delivery history is separated from the current delivery status.

We intentionally retain product name and price snapshots in `order_items`. This is historical transaction data, not an accidental normalization violation.

# 5. Advanced DBMS features to implement

These are the features that will distinguish the project academically.

| DBMS concept             | Implementation                         |
| ------------------------ | -------------------------------------- |
| Primary and foreign keys | All relational entities                |
| Constraints              | NOT NULL, UNIQUE, CHECK                |
| Normalization            | 1NF, 2NF, 3NF                          |
| Joins                    | Product, inventory, order reports      |
| Subqueries               | Customer and sales analysis            |
| Views                    | Sales, stock and delivery reports      |
| Stored procedures        | Checkout, cancellation, stock transfer |
| Functions                | Calculate order total, available stock |
| Triggers                 | Inventory audit, order history         |
| Transactions             | Checkout and stock reservation         |
| Concurrency              | Simultaneous purchase testing          |
| Indexing                 | Order, inventory and product searches  |
| Query optimization       | EXPLAIN ANALYZE                        |

### Suggested stored procedures

1. `sp_place_order`
2. `sp_cancel_order`
3. `sp_add_inventory`
4. `sp_transfer_inventory`
5. `sp_assign_delivery`
6. `sp_release_expired_reservations`

### Suggested triggers

1. `trg_inventory_audit` — logs inventory modifications.
2. `trg_order_status_history` — maintains order status history.
3. `trg_delivery_status_history` — records delivery updates.
4. `trg_validate_order_item` — validates order item quantities and prices.

For audit triggers, we should avoid relying on them for all business logic. The application and stored procedures will control the transaction, while triggers record relevant changes.

### Suggested views

- `vw_available_products`
- `vw_low_stock`
- `vw_daily_store_sales`
- `vw_customer_order_history`
- `vw_delivery_performance`

## 10. Important implementation decisions

Before writing the SQL, let's establish a few rules:

1. One MySQL database: `quickkart_db`.
2. One primary relational database: No premature sharding or microservices.
3. Store-specific inventory: Never maintain stock directly in the products table.
4. Transaction-safe checkout: Inventory reservation and order creation must be atomic.
5. No real payment processing: Simulate payment success, failure and refunds.
6. No real-time GPS requirement: Delivery status updates are sufficient for the initial version.
7. Use seeded data: Multiple Chennai dark stores, customers, delivery partners and grocery products.

For inventory, we'll enforce:

\\[ 0 \leq ReservedQuantity \leq TotalQuantity \\]

For checkout, we will use InnoDB transactions, `SELECT ... FOR UPDATE`, and rollback on failure.

One more detail: when an order is placed, we should save a snapshot of its delivery address as well, so changing a customer's saved address later doesn't alter an old order.
